# ビジュアル設計（盆栽の3D表現・成長・季節）

apps/web で盆栽をどう見せるかの設計。成長段階・季節・活力・個体差・アニメーション・レイアウトの「正」とする。
実装スタックは Three.js + React Three Fiber（[architecture-design.md](architecture-design.md) §2.2）。

## 1. 方針

- **アートディレクション**: スタイライズド / ソフトな低ポリ。クリーンな幾何形＋落ち着いた配色。**プロシージャル生成**（コードで生成）を基本とし、3D アセットの外部制作には依存しない。
- **世界観**: 「癒し・ゆっくり・競争させない」。派手な演出・定量的な競争表現は避ける。
- **本物の盆栽に忠実**: 成長の到達点は「満開」ではなく、**樹形の完成・古木の風格**（侘び寂び）。花は「成長の終点」ではなく**季節の表情**として扱う（§3）。

## 2. 成長：2フェーズモデル

盆栽の状態は「成長フェーズ」→「維持・循環フェーズ」の2段構えとする。**いずれも後退しない**（成長段階は単調・不可逆、維持フェーズから成長フェーズへ戻らない）。**枯死・劣化などのマイナス要因は持たない**。

### 2.1 成長フェーズ（6段階）

活動量に応じて、以下の6段階（`stage` 番号 1..6）を一方向に進む。

| `stage` | 段階（名前ラベル） | キー(例) | 見た目の要点 |
|---|---|---|---|
| 1 | 実生 | `seedling` | 芽生え。小さな双葉・細い軸 |
| 2 | 若木 | `young` | 細い幹と数本の枝。葉が出始める |
| 3 | 幹の成長 | `trunk` | 幹が太く・曲がりが出る。樹勢が増す |
| 4 | 仕立て | `branching` | 枝が分かれ骨格が形成される |
| 5 | 成熟 | `mature` | 葉が充実し樹形が整う |
| 6 | 風格 | `refined` | 古木の趣・完成した樹形（成長フェーズの到達点） |

- 描画入力としては `stage` 番号（1..6）を受け取る。名前（実生/若木/…/風格）は番号に対応する表示ラベルとして扱う。
- 段階の境界（閾値）と `stage` 番号↔見た目の対応は、apps/api の成長ルール（コード定数）で定義する（単一の正）。
- 段階数・キーは確定値ではなく設計意図を示す。実装時に apps/api の成長ルールと整合させる。

### 2.2 維持・循環フェーズ（永続）

「風格」到達後は**終わりではなく**、季節の循環と日々の活力で**生き続ける**フェーズに入る。盆栽は後退せず、季節（§3）と活力（§4）で姿が変わり続ける。

- このフェーズは独立した項目では持たない。`stage` の終端（6=風格）に居ること自体が「維持・循環フェーズ」を表す（`stage` 終端からの派生）。

### 2.3 進捗表現（ゆるい）

- 生のカウント（発言数・リアクション数・感謝数）や競争的な進捗バーは**出さない**。
- 前進感は**盆栽そのものの変化**と、やわらかな段階インジケータ程度で伝える（数値での競争を煽らない）。

## 3. 季節

- **現実の季節（実時間）に同期**する。人工的な短縮サイクルは採らない（現実との共鳴＝アンビエントの強み、および「ゆっくり」哲学の維持のため）。
- **四季すべてを魅力的に**する（「春だけが見どころ」にしない）。
- **盆栽だけでなく周囲の環境（背景・光・舞う粒子）も季節で変える**（小さな盆栽単体では季節差が分かりにくいため）。
- 季節遷移は**ゆるやかなクロスフェード**。

| 季節 | 環境アンビエント（受動・常時） |
|---|---|
| 春 | 花びらが舞う・柔らかい光 |
| 夏 | 濃い緑・強い陽射し |
| 秋 | 落ち葉・琥珀色の光 |
| 冬 | 雪・澄んだ静けさ |

## 4. 活力（活動への応答）

日々の分報活動に応じて、盆栽が「活き活きする」表現を**加点的**に行う。

- **季節に合った姿**で活力を表す（冬に桜を咲かせない等、季節の整合を守る）。

| 季節 | 活動による活力表現 |
|---|---|
| 春 | 開花（桜・花） ← 花の主役はここ |
| 夏 | 青葉が瑞々しく茂る・新芽が伸びる |
| 秋 | 紅葉が深く色づく・実が生る |
| 冬 | 常緑の艶・雪が映える・春への新芽の兆し（花は出さない） |

- **加点的・非懲罰**: 活動で映えるが、非活動でも**枯れず穏やかに保たれる**（マイナスにしない）。動機づけは「失う恐れ」ではなく「映える喜び＋季節の新鮮さ」に置く。
- この活力（`vitality`）は apps/api がサーバ側で調理する。最終活動時刻（`last_active_at`）からの減衰として 0..1 で算出し、未活動でも穏やかな下限値に留める（クライアントは受け取った値を描くだけ）。

## 5. 個体差

- **単一の樹種**を基本とし、ユーザーごとの**シード値**（`seed`）で見た目を変える（幹の曲がり・枝ぶり・プロポーション・鉢・微妙な色味）。`seed` は `user_id` から決定論的に算出され、apps/api がサーバ側で生成して返す（保存しない）。
- スタイルは統一しつつ、チーム一覧で**各メンバーを見分けられる**程度の差を出す。
- 将来拡張: 複数の**樹種**割当（松/桜/もみじ/南天…）で、季節の見せ場を個人ごとに変える（MVP では行わない）。

## 6. アニメーション

控えめ・ゆっくり・有機的を基本とする。

- **常時アンビエント**: そよ風の微揺れ＋季節の粒子（花びら/落ち葉/雪）＋柔らかな光のゆらぎ。軽量に。
- **成長遷移**（段階アップ時）: ゆっくり有機的に成長（枝が伸び葉が開く）＋淡い光。**静かだが嬉しい**程度に留める（大げさな演出はしない）。
- **季節遷移**: ゆるやかなクロスフェード。
- **活力・開花**: じんわり現れる穏やかな表現。
- **性能（LOD）**: 個別ページ=フル表現／チーム一覧=簡略表現（揺れ・粒子を控えめ/間引き）。

## 7. レイアウト

- **個別の盆栽閲覧ページ（MVP）**: **風景（背景）＋フル季節アンビエント**で没入的に見せる。
- **チーム盆栽一覧（MVP）**: **盆栽棚（段組みグリッド）**。盆栽コレクションの飾り方に忠実で、見分けやすく・人数にスケールし（行＋スクロール/パン）・性能も管理しやすい。各盆栽に表示名/アバター、タップで個別ページへ。
- **将来拡張**: 共有の庭/風景に盆栽を配置するレイアウト（機能追加フェーズで段階的に導入）。

## 8. データとの対応

描画入力はすべて apps/api がサーバ側で調理してレスポンスに載せる。クライアント（apps/web）は受け取った値を描くだけで、成長・季節・活力・個体差の計算はしない。本設計が要求する描画入力は次の素の項目で表す。

- **`stage`**: 成長段階の序数（1..6。§2.1）。番号↔見た目の対応は apps/api の成長ルール（コード定数）が正。
- **`seed`**: 個体差シード（§5）。`user_id` から決定論的に算出してサーバ生成する（保存しない）。
- **`vitality`**: 活力（直近の活動に基づく“映え”の度合い。§4）。`last_active_at` からの減衰として 0..1 でサーバ算出する（保存しない）。
- **`season`**: 季節（§3）。サーバがレスポンス時刻（基準TZ=JST）から導出する。シーン共通（全員同じ）なのでレスポンスでは最上位に置き、盆栽ごとには持たない（保存しない）。

`stage`/`seed`/`vitality` は盆栽ごとの描画入力としてレスポンスの `render` に、`season` はシーン共通として最上位に載る（構造は [api-design.md](api-design.md)）。

保存される項目（`last_active_at` など、`vitality` の算出元）の詳細スキーマは [database-design.md](database-design.md) で定義する。
