# ADR-001: PostgreSQLを採用する

## Status

Accepted

## Context

たま森では、Slack上の活動を内部の活動イベントへ変換し、活動ログとして保存する。
その活動ログを元に、ユーザーごとの盆栽状態を更新する。

MVPで扱う主なデータは以下である。

- チーム
- ユーザー
- 活動ログ
- 盆栽状態

この設計では、以下の性質が必要になる。

- チーム、ユーザー、活動ログ、盆栽状態の関係を明確に扱えること
- チーム単位でデータを分離できること
- SlackイベントIDを使って重複イベント処理を防げること
- 活動ログ保存と盆栽状態更新を整合性を保って処理できること
- 将来的な活動統計や集計に拡張しやすいこと

## Decision

MVPのDBにはPostgreSQLを採用する。

PostgreSQLの外部キー制約、一意制約、トランザクションを利用して、データの整合性を保つ。

## Consequences

### Positive

- リレーションを自然に表現できる。
- SlackイベントIDに対する一意制約で、重複イベント処理を防ぎやすい。
- 活動ログ保存と盆栽状態更新をトランザクションで扱いやすい。
- 発言数、リアクション数、感謝数、活動量の集計に対応しやすい。
- 将来的な活動統計やグラフ表示へ拡張しやすい。

### Negative

- Cloud Runから接続する場合、接続数管理やコネクションプールを考慮する必要がある。
- NoSQL系DBと比べると、スキーマ変更時にマイグレーション設計が必要になる。
- 運用時にバックアップ、マイグレーション、接続管理を適切に扱う必要がある。

## Alternatives

### Firestore

- サーバーレスで扱いやすい。
- リアルタイム更新との相性は良い。
- 一方で、今回の中心であるリレーション、集計、整合性の扱いはPostgreSQLの方が素直である。

### DynamoDB

- 高スケールなイベントログ用途に強い。
- トランザクションも利用できる。
- 一方で、アクセスパターンを前提にした設計が必要で、MVPでは設計難度が上がる。

### MySQL

- RDBとして安定している。
- PostgreSQLと同様に候補になり得る。
- 今回はPostgreSQLの制約、トランザクション、集計の扱いやすさを優先する。

### MongoDB

- 柔軟なドキュメント構造に強い。
- 一方で、今回のデータ構造はリレーションが明確であり、優先度は低い。
