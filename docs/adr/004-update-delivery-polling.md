# ADR-004: 盆栽状態の更新反映にポーリングを採用する

## Status

Accepted

## Context

requirements.md・architecture.md は当初、盆栽状態の更新反映の手段として WebSocket を前提していた。複数インスタンス（Cloud Run）での fan-out 方式（#91）を決める前に、そもそも WebSocket が必要かを再検討した。

本サービスの性質は以下である。

- 盆栽は「ゆっくり育つ」メタファーで更新頻度が低く、秒単位の即時反映に本質的価値が薄い。
- 更新はサーバ→クライアントの一方向で、クライアントが接続経由で送る情報は無い（双方向は不要）。
- 盆栽状態はスナップショット型で、最新値が取れればよく、メッセージ欠損や厳密な順序保証は不要。
- 規模は小さい（分報ベース・チーム単位）。

WebSocket の強み（双方向・低遅延・高頻度）はいずれも要件と噛み合わない。一方で Cloud Run 上で WebSocket を使うと、持続接続の管理・複数インスタンス間の fan-out（#91）・接続課金といった複雑さとコストを負う。SSE も一方向 push だが、持続接続のため fan-out の問題はポーリングと違って残る。

実サービスの傾向（クラス対応）でも、双方向・協調的なアプリ（Slack / Discord / Trello 等）は WebSocket、一方向ストリーミング（ChatGPT / Claude 等）は SSE、低頻度・スナップショットのダッシュボードはポーリング、という住み分けがあり、本サービスは最後のクラスに該当する。

## Decision

盆栽状態の更新反映は **ポーリング**（apps/web が apps/api の HTTP API を一定間隔で再取得する。SWR の `refreshInterval`、目安 30〜60 秒）で行う。WebSocket・SSE は採用しない。

- apps/api は **stateless な HTTP API のみ**を提供し、持続接続・push 配信は持たない。
- これにより複数インスタンス間の fan-out（#91）は不要となる（#91 はクローズ）。
- 初期表示も更新反映も同じ HTTP 取得経路に一本化する（初期表示＝初回取得、更新＝定期再取得）。
- 反映間隔は要件に応じて調整可能とする（既定 30〜60 秒）。

## Consequences

### Positive

- 実装が最小（SWR は既に導入済み。`refreshInterval` を設定するだけ）。
- apps/api が stateless に保たれ、Cloud Run と相性が良い（scale-to-zero 可、接続管理不要）。
- 複数インスタンス間 fan-out・接続管理・再接続処理が一切不要（#91 解消）。
- 初期表示と更新が同一経路でシンプル。インフラ追加（Redis / Pub/Sub 等）が不要でコスト最小。

### Negative

- 更新が画面に反映されるまで最大「ポーリング間隔ぶん」の遅延が生じる（例 30 秒）。「ゆっくり育つ」性質上、実用上の問題は小さい。
- 更新が無くても定期リクエストが発生する（小規模・低頻度のため量は些少。間隔調整で制御可能）。
- 秒単位の即時性や双方向通信が必要な機能を将来導入する場合は、その機能に限って SSE / WebSocket を再検討する。

## Alternatives

### WebSocket

- 双方向・低遅延の即時 push が可能。
- 一方で本サービスは双方向・高頻度ではなく過剰。Cloud Run 上では持続接続の管理・複数インスタンス間 fan-out（#91）・接続課金が必要になり、シンプルさを損なう。採用しない。

### SSE（Server-Sent Events）

- サーバ→クライアントの一方向 push で WebSocket より単純。
- 一方で持続接続を保持するため、複数インスタンス間の fan-out 問題はポーリングと違って残り、Cloud Run 上のシンプルさという観点での利点が小さい。採用しない。

### 更新反映なし（都度取得のみ）

- 画面を開いた時だけ最新を取得する。最小実装だが、開いたまま放置すると古い状態が残り「自動反映」の要件を満たさない。ポーリングの方が要件に合う。
