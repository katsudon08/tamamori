# ADR-006: 成長ルールを apps/api のコード定数として持つ

## Status

Accepted

## Context

盆栽の成長段階（`stage`）を決めるルール——活動種別ごとの重み、`activity_score` の閾値、`stage` の序数と見た目の対応——を「どこに置くか」が論点だった。DBに `growth_rules` テーブルを設けるか、apps/api のコードに持つか。

requirements.md §4 は「チームごとの成長ルール設定」を将来検討に置いており、MVP ではユーザー・管理者が閾値を変える要件はない。類似サービス（Duolingo / Forest / 育成ゲーム等）でも成長・レベルの閾値は製品固定の定数で、エンドユーザーは変更しないのが一般的である。閾値を変えられるのは管理者向けゲーミフィケーション系に限られ、それは requirements.md §4 が対象外とする「管理者向けの詳細な設定画面」に該当する。

## Decision

成長ルール（活動種別の重み、`activity_score` の閾値、`stage` の序数↔名前/見た目パラメータの対応）は **apps/api のコード定数を単一の正**とする。DBに `growth_rules` 等のルール用テーブルは設けない。

- DBが持つのは計算結果（`activity_score`, `stage`）のみ。`activity_logs（正）→ activity_score（重み付き和）→【apps/api の閾値】→ stage`。
- 重みは**単一スコア方式**（重み付き和。頻出する活動ほど重みを小さく、稀な活動ほど大きく）とする。

## Consequences

### Positive

- ルールが製品コードと共にバージョン管理され、変更履歴・レビューに乗る。テーブル・シード・管理画面が不要で実装が最小。
- DBはスナップショットに専念し、責務が明確になる。
- docs（visual / api / database）はルールの所在（apps/api）を指すだけになり、重複定義（DRY違反）を避けられる。

### Negative

- 閾値の変更にはデプロイが必要（MVPでは頻繁な変更を想定しないため許容）。
- 「チームごとの成長ルール」を実装する段階では、`growth_rules` テーブル等への移行が必要になる。

## Alternatives

### growth_rules を DB テーブル化する

- デプロイなしで閾値を変更でき、チームごとのルールへ拡張しやすい。
- 一方でユーザー・管理者が閾値を変える要件は現状なく（管理者設定は requirements.md §4 で対象外）、テーブル・シード・将来的な管理UIのコストを早期に負う。将来「チームごとの成長ルール」を実装する時点で導入すればよい。現時点では採用しない。

### 多要素ルールで stage を判定する

- 複数軸の条件（msg≥X かつ reaction≥Y …）で判定する。表現力は高い。
- 一方でルールが複雑でチューニングが難しい。MVPは重み付き単一スコアで「多要素」を表現でき十分。偏りが顕在化したら切り替える。現時点では採用しない。
