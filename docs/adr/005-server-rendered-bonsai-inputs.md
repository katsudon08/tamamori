# ADR-005: 盆栽の描画入力をサーバが調理し apps/web はビューアに徹する

## Status

Accepted

## Context

visual.md が要求する盆栽の描画入力（成長段階・個体差・活力・季節）を「どこで生成するか」が論点だった。seed を `user_id` から、season をクライアント時計から、vitality をクライアント計算で導出する案もあり得た。

前提として、apps/web は画面表示に専念し（FE/BE 分離）、更新反映はポーリング（[ADR-004](004-update-delivery-polling.md)）で行う。ポーリングのたびにサーバが現在時点の値を返せる構造である。

## Decision

盆栽の描画入力（`stage` / `seed` / `vitality` / `season`）は **すべて apps/api がサーバ側で生成（調理）してレスポンスに載せる**。apps/web は受け取った値を描画するビューアに徹し、成長・季節・活力・個体差の計算をしない。

- `stage`: `bonsai_states.stage`（序数）をそのまま載せる。
- `seed`: `user_id` から決定論的に算出（hash）。保存しない。
- `vitality`: `now - last_active_at` の減衰として 0..1 で算出。保存しない。
- `season`: レスポンス時刻（基準TZ=JST）から導出。シーン共通のためレスポンス最上位に置く。保存しない。
- 生カウント（発言数等）・`activity_score` はサーバ計算の内部値で、レスポンスに含めない。

## Consequences

### Positive

- フロントが純粋なビューアになり、表示とドメイン計算が分離されて保守しやすい。
- 季節・活力の算出ルールが apps/api に一元化され、クライアント実装差・ドリフトが生じない。
- クライアントに生カウントを渡さないため、「競争を煽らない」方針（visual-design §2.3）を技術的に担保できる。
- レスポンスが描画に必要な値だけになり小さい。

### Negative

- `season` / `vitality` はレスポンス時点のスナップショットで、ポーリング間隔ぶん古くなりうる（ゆっくり変化するため実用上の影響は小さい）。
- `season` のサーバ導出は基準TZを前提とする（MVPは単一TZ=JST。多地域対応は将来課題）。
- オフライン描画などクライアント単独で描画入力を導出したいケースが将来生じたら再検討する。

## Alternatives

### クライアント側で導出する

- seed は `user_id`、season はクライアント時計、vitality はクライアント計算で導出できる。
- 一方でフロントが計算責務を持ち「ビューアに徹する」分離に反する。クライアント実装差や端末TZ依存のばらつきを生む。採用しない。

### visual_state として1つの集約に束ねる

- 描画入力を1つのオブジェクト/カラムにまとめる案。
- 一方で描画入力は素の項目（stage/seed/vitality/season）に分解でき、束ねる必要がない（早すぎる抽象）。採用しない。
