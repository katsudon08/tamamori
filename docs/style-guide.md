# ドキュメント記述規格

`docs/` 配下の設計ドキュメント（`requirement.md` / `architecture.md` / `api.md` / `database.md` など）で共通して用いる記述規格を定義する。新規ドキュメントの作成時や既存ドキュメントの更新時は、本規格に従う。

## 1. H1見出し

ドキュメントの内容を表す日本語にする。ファイル名は使わない。

- `requirement.md` → `# 要件定義`
- `architecture.md` → `# アーキテクチャ設計`
- `api.md` → `# API設計`
- `database.md` → `# データベース設計`

## 2. セクション見出し

`##`（トップレベルのセクション）には連番をつける。

- `## 1. システム概要`、`## 2. 技術スタック` のように記述する。
- `###` 以下の小見出しには連番をつけない。

## 3. 文体

である調（「〜である」「〜する」「〜しない」）で統一する。です・ます調は使わない。

## 4. 箇条書き項目の語尾

リスト項目の語尾は用途で使い分ける。同一リスト内ではスタイルを混在させない。

- 説明・方針・処理を述べる文 … 「〜する。」と句点で終える文にする。
- 要件を述べる文 … 「〜できること。」で揃える。
- 純粋な列挙（カラム名・項目名・技術名など名詞の列挙）… 体言止め・句点なしにする。

## 5. ドメイン概念の表記

ドキュメントの層に応じて表記を分ける。

- `requirement.md` … 日本語のドメイン概念（チーム / ユーザー / 活動ログ / 盆栽状態）で記述する。
- `database.md` … 物理スキーマで記述する。エンティティは `Team` のようにPascalCase、テーブル・カラムは `snake_case` をバッククォートで囲む。
- `database.md` の冒頭で、日本語のドメイン概念と物理名（テーブル / エンティティ）の対応を明示し、層をまたいだ参照を橋渡しする。

## 6. 導入句

列挙の前置きは「主な〇〇:」で統一する（主な用途 / 主な処理 / 主なカラム / 主な表示内容 / 主な操作 など）。

## 7. 強調

太字（`**`）は初出のキー概念や固有名詞の強調に限定し、多用しない。
