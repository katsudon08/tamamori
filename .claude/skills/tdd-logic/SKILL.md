# TDD ロジック実装ガイドライン

ロジックやモジュールの実装を TDD で行う際、以下のルールに従うこと。

## TDD 手順

必ず Red → Green → Refactor の順に進める。

### 1. Red（テスト作成）

- テストファイルを先に作成する
- テストを実行し、**失敗することを確認**してから次へ進む

### 2. Green（実装）

- テストを通す最小限のコードを実装する
- テスト通過後、**型チェック (`tsc --noEmit`) と lint (`eslint`) を実行**する

### 3. Refactor（リファクタリング）

- コードの整理・保守性向上を行う
- 完了後、**テスト・型チェック・lint を再度すべて実行**し整合性を確認する

## テストファイル規約

### 配置・命名

- テストファイルは `__tests__/*.test.ts` に配置する
- テストタイトル（`describe`, `test` の引数）は**日本語**で記述する

### import

Jest のグローバル関数は**必ず `@jest/globals` から明示的に import** する。グローバル変数に依存しない。

```ts
// OK
import { describe, test, expect, jest, beforeEach } from '@jest/globals';

// NG — 暗黙のグローバル使用
describe('...', () => { ... });
```

### テスト構造

- 正常系・異常系が混在する場合は `describe` をネストして分類する
- テストケースが少数（目安: 3件以下）の場合はフラットでもよい

```ts
// ネスト推奨の例
describe('parseEnv', () => {
  describe('正常系', () => {
    test('全変数が設定されている場合、型付きオブジェクトを返す', () => { ... });
  });
  describe('異常系', () => {
    test('必須変数が欠損した場合にZodErrorをthrowする', () => { ... });
  });
});
```

## モック方針

| 対象 | 方針 |
|---|---|
| 外部サービス（Supabase, Slack API 等） | モックする |
| 他スライスの依存（FSD レイヤー間） | モックする |
| 同一スライス内のユーティリティ | 実コードを使う |

各スライスは単体で完結するテストとし、他スライスの変更でテストが壊れることを防ぐ。

## 副作用の分離

モジュールがトップレベルで副作用（起動時バリデーション等）を持つ場合、**純粋な関数を別ファイルに分離**してテスト可能にする。

```
config/
  env-schema.ts  ← 純粋な parseEnv() をここに定義（テスト対象）
  env.ts         ← parseEnv() を呼び出して env 定数をエクスポート（副作用あり）
```
